# 10 — Roadmap, Risks, and Open Questions

## Build phases

Each phase ends with something a real project can run in its pipeline. No phase depends on a
later one to be useful — this de-risks the whole effort.

### Phase 1 — The deterministic skeleton (no AI) · ~3–4 weeks
**Goal: `vigil run --url X` produces a genuinely useful verdict with zero LLM calls.**
- Orchestrator, budgets, worker pool, context isolation
- Discovery: sitemap + crawl tiers (+ Next.js code adapter as the first of the family)
- NetworkRecorder + T1 render-integrity signals + T2 contract *recording* on first visit and
  *checking* thereafter (the contract mechanism needs no AI at all)
- Visual baseline capture + diff (no masks yet — visual failures are yellow-only in this phase)
- AssetStore (contracts, baselines, index; no specs yet), Reporter (cli, json, html, exit codes)
- **Exit criterion:** dogfood on 3 real apps; the tool catches an injected chunk-404, an injected
  API 500, and a blank-render — each in under 60 seconds, with zero false reds across 50 clean runs.

Phase 1 is the trust foundation and, importantly, a shippable product on its own
("smart smoke tests, zero config").

### Phase 2 — The brain (explore, cache, run) · ~4–6 weeks
**Goal: the cache hit/miss loop is real.**
- ModelClient; Explorer (a11y-snapshot loop, safety model, spec emission, self-check)
- Fingerprinter (normalization, hashing, similarity) + hit/miss resolution in the Orchestrator
- Runner executing cached specs; masks generated by Explorer; `--no-ai` mode
- **Exit criterion:** on the dogfood apps, run #2 is ≥90% cheaper and ≥5× faster than run #1;
  generated specs read like idiomatic Playwright to a reviewer.

### Phase 3 — Trustworthiness (triage, heal, flake control) · ~4 weeks
**Goal: a red light people believe.**
- Triage rules + retry probe + LLM triage; Healer with diff-size guard; strikes & quarantine;
  environmental-flake run retry; baseline/mask/contract self-maintenance policies
- **Exit criterion:** across a month of dogfooding with deliberate UI churn, ≥80% of drift-caused
  failures self-heal, and zero stale-test failures reach a human as "BROKEN".

### Phase 4 — Distribution · ~3 weeks
- GitHub Action; Slack/Jira/GitHub reporters; MCP server + Claude Code skill; docs site;
  remaining framework adapters (community-contributable by design)
- VS Code extension deferred until demand proves it.

## Top risks and their mitigations

| Risk | Why it's real | Mitigation (already designed in) |
|---|---|---|
| **False positives kill trust** | The #1 reason E2E tools get abandoned | Whole of doc 06: authority tiers, triage-before-red, healing, quarantine, INCONCLUSIVE runs, evidence with every red |
| **Fingerprint mis-calibration** | Too sensitive → constant expensive re-exploration; too loose → stale specs pass on changed pages | Similarity (not equality) with tunable thresholds; the spec run itself is the backstop; telemetry on hit-rate + heal-rate to tune defaults empirically in Phase 2 dogfooding |
| **LLM cost surprises** | Agents without budgets are bills | Hard `maxLlmCostUsd` per run; misses degrade to UNVERIFIED, never overspend; hits-first scheduling; `--no-ai` mode |
| **Agent safety against production** | One wrong click submits an order | Read-mostly default, non-disableable destructive denylist (extendable only), form-abandon rule, request-level route blocking, full trace audit (05) |
| **SPA/canvas apps with poor a11y trees** | Fingerprint and locators both depend on the a11y tree | Screenshot-assisted exploration fallback; visual+contract lanes still function; honestly reported as reduced-confidence coverage |
| **Auth complexity (SSO/MFA)** | Blocks the "everything is behind login" majority | storageState reuse + scripted login + agent-bootstrapped login script (03); TOTP support v1.1; document the test-account pattern |
| **Generated-spec quality ceiling** | Industry experience: generation gets ~80% there | Self-check gate before `active`; specs are reviewable plain Playwright; humans can edit (healer respects it) or delete (regenerate) |
| **Scope creep toward "QA platform"** | Every user will ask for their favorite feature | The non-goals list in 01 is a contract; custom `Check` extension point absorbs edge demands without core growth |

## Open questions (decide during Phase 1–2, with data)

1. **Fingerprint thresholds** — 0.90/0.60 are educated guesses; dogfood telemetry decides.
2. **Contract merging across samples of one route** — one contract per pattern (current design)
   vs per-sample when samples behave differently (e.g. empty vs full cart). Leaning: per-pattern
   with union schemas, split only on observed divergence.
3. **Spec granularity** — one spec per route (current) vs allowing the Explorer to emit an extra
   cross-route *flow* spec for things like login→dashboard. Flows are the most valuable and the
   most dangerous (state-changing); likely v2 behind `allowSubmit`.
4. **Shared store backend** — teams running vigil from many CI machines share via git today;
   is that enough, or is a remote StoreBackend (S3/DB) needed sooner than v2?
5. **Model tiering** — how far down can triage/heal go on small cheap models before quality
   drops? Structured-output evals in Phase 3.
6. **Name** — `vigil` is a working name; check npm availability and trademark before Phase 4.

## What success looks like (12 months out)

A team installs vigil in ten minutes, forgets it exists, and six weeks later a Slack message
reads: *"❌ /checkout — payment API returning 500 (was 2xx for 214 runs) — trace attached"* —
ninety seconds after the deploy that caused it, before the first customer complaint. Their
`.vigil/` directory contains a 60-spec Playwright suite nobody wrote, that has quietly healed
itself through four redesigns.
